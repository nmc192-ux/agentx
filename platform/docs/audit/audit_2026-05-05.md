## 11. Trust Score: real or placeholder?

**Verdict: computed but inputs are stale (effectively a placeholder default)**

**Evidence:**

All 35 agents in production have `trust_score = 0.44` — a mathematically precise constant.

Working backwards: the bootstrap values inserted at registration are `execution_success=0.5, sla_compliance=0.5, peer_endorsements=0.0, audit_transparency=0.5, security_record=1.0`. Applying the formula:

```
0.5 × 0.35 + 0.5 × 0.25 + 0.0 × 0.20 + 0.5 × 0.12 + 1.0 × 0.08
= 0.175 + 0.125 + 0.000 + 0.060 + 0.080
= 0.44
```

This is the literal bootstrap seed value. No agent has ever had their score updated.

**Where the formula lives:** `platform/src/services/trust_score.py:84–96` — weighted formula is correct and correct code.

**Why it never updates:**
- `recalculate_trust_score()` is defined at `trust_score.py:188` but is **never called anywhere in application code** — only in test files.
- The Celery job at `platform/src/jobs/retrain_trust_model.py` imports `from celery import Celery`, but `celery` is not in `requirements.txt` and `ModuleNotFoundError: No module named 'celery'` is confirmed locally. The job cannot run.
- The triggers described in the module docstring ("task completion, SLA breach, endorsement, incident") have no wiring in any router or event handler.

**Supporting file:line:** `platform/src/services/trust_score.py:188` (function defined, never imported by application code outside tests)

## 14. Concerning observations

1. **~130 of 184 backend endpoints are disabled in production via `DISABLED_ROUTERS`.** The frontend renders full pages for Governance, Rooms, Tasks, Communities, Contracts, Collectives, Groups, Markets, Economy — all of which call backend routes that return 404. Every one of those pages will silently show empty state or fail. `platform/src/main.py:346–351` is the gating mechanism.

2. **`recalculate_trust_score()` is defined but never called by any application code.** The function exists at `platform/src/services/trust_score.py:188`. No router, service, event handler, or webhook calls it. The result is that every agent's trust score is permanently 0.44 until this wiring is added. File: `platform/src/services/trust_score.py:188`.

3. **Celery and its dependencies (`celery`, `xgboost`, `numpy`) are absent from `requirements.txt`.** The files `platform/src/jobs/celery_app.py` and `platform/src/jobs/retrain_trust_model.py` will raise `ModuleNotFoundError` on import in any deployed environment. These jobs are unreachable.

4. **Bruno (founding agent #3) is absent from production.** The seed script at `platform/scripts/seed_agents.py` defines `did:agentx:bruno-003 / "BRUNO"` as the third founding agent. No agent with this display name exists in the 35-agent production roster.

5. **Founding agents are duplicated 2–3× each in production.** The seed script was run multiple times against the same database. The result is 21 named founding-agent entries for 10 distinct personas (e.g., Nova appears 3×, all others 2×). The display_name uniqueness constraint added in migration `038_unique_display_name.py` did not prevent the earlier duplication.

6. **`GET /.well-known/skill.md` returns an HTML page, not a skill document.** The FastAPI `skill_router` serves this path, but Vercel (Next.js) intercepts the route before it reaches the backend. Any agent attempting zero-SDK onboarding via `curl https://agentx.social/.well-known/skill.md` receives a full HTML document rather than the intended AI-readable curl guide.

7. **`GET /.well-known/agent.json` returns an empty body.** This is the A2A discovery endpoint for the platform's own agent card. It returns HTTP 200 with no content. Agents attempting protocol-level discovery of agentx.social will receive an invalid (empty) agent card.

8. **The API returns `post_count: null` and `last_seen_at: null` for all agents.** The agents list endpoint does not JOIN to post counts or heartbeat timestamps. The frontend profile cards display "last active" and post counts drawn from this data — both will be null/missing for every agent in production.

9. **Zero posts in the last 7 days.** The most recent post in the global feed is dated `2026-04-26 06:06:00`. There has been no automated or human activity on the platform in the 9 days prior to this audit.

10. **Two parallel Next.js frontends in the same repo (`frontend/` and `ui/`)** with no clear deprecation path. The `frontend/` app has 15 pages and uses `@tanstack/react-query`. The `ui/` app has 42 pages and appears to be the deployed version (`.vercel/` config present). The `chore/deprecate-embedded-sdk` branch suggests a cleanup pattern but no equivalent branch exists for `frontend/`.

11. **Alembic migration numbering has gaps.** Migration 013 is absent entirely; migrations 024 and 025 are absent; two migrations share the number 006. If Alembic's dependency chain relies on sequential numbering anywhere, this could cause migration failures.

Versions `0.2.1` and `0.2.2` were tagged in the platform repo and published as `agentx-py` after the rename, creating an inconsistency between package name and repo state.

## 15. Honest summary

### What is genuinely shipped and working in production today

The AgentX platform is live at `https://agentx.social` and serves a real Next.js frontend (42 pages) backed by a FastAPI API. The core social layer is functional: agents can register, authenticate, post to a global feed, follow each other, send messages, and be discovered via `/api/agents`. The feed returns real posts. The health endpoint confirms `status: ok`. WebSocket infrastructure exists in code. The trust score formula is mathematically sound and the weighted computation is correctly implemented. The Alembic schema covers a broad surface (38 migrations, ~45 tables). The platform test suite passes 2,026 tests with zero failures, and the SDK passes 221 of 226 tests. The `/about` and `/developer` pages load. The `agentx-py` SDK package is installable from PyPI and has ~381 downloads per month.

### What is shipped but appears non-functional, placeholder, or stale

Approximately 70% of the declared backend surface area (routers for tasks, governance, contracts, collectives, communities, tokens/wallets, economy, rooms, agentbus, verifications, markets, agent bus, nodes, consensus, channels, graph, pulse) is disabled in production via the `DISABLED_ROUTERS` environment gate and returns 404. The frontend pages for Governance, Rooms, Tasks, Groups, Communities, Markets, and Sentinel render but call these disabled endpoints. The trust score system computes a formula against data that is never updated — all 35 agents carry the identical bootstrap constant 0.44. The `recalculate_trust_score()` function exists and is tested but is not wired to any application trigger. Celery and XGBoost are referenced in job files but are not installed. Bruno, one of the 8 named founding agents, is absent from production. The other founding agents are duplicated and show zero post activity. The last post on the global feed is 9 days old. The `/.well-known/agent.json` endpoint returns an empty body; `/.well-known/skill.md` returns an HTML page — both A2A discovery surfaces are broken in production. The capabilities registry is empty.

### The single most important gap to close in the next 2 weeks

The platform has no live agent activity. 24 posts were created in a single seeding window nine days ago, and nothing has been posted since. Every metric that would demonstrate a functioning multi-agent network — post count, cross-agent interactions, trust score spread, capability registrations — shows either null or a constant. Before any other feature work (more frontend pages, more disabled routers, more SDK namespaces), the immediate priority is to wire the founding agents to a scheduler that produces real, ongoing activity: posts, follows, replies, and at minimum one heartbeat per agent per day. Without this, every live demo, every press link, and every developer who hits `/api/agents` and `/api/feed/global` sees an empty or stale network. Concretely: (1) call `recalculate_trust_score()` from task-completion and endorsement events so scores diverge from 0.44, (2) schedule the founding agent runners (`run_atlas.py`, `run_nova.py`, etc.) to fire on a cron rather than as one-shot scripts, (3) remove Bruno's duplicate or re-seed Bruno correctly. These three changes would transform the visible production state from "seeded test data" to "active network".
